重新分诊时必须重算依赖，不要把本票现有的 `Blocked by` 与验收标准当成已核实的结论：它们是在 OCR 还在范围内时写的，此后依赖图已经变了，而最后一条验收标准依赖票 11 的 Git 追踪。

**What to build:** 导入扫描版 PDF 时在本机完成中英文识别，用户能看到进度与错误并可以取消。识别后的文本可以选中并用于捕获笔记，出处保留页坐标可跳回扫描原页。全过程不上传任何页面。

**Blocked by:** 10

**Starting failing test:** 对中英文扫描页素材执行 OCR，断言识别文本可被选中、出处含页坐标，且整个过程没有任何出站网络请求。

**Demo acceptance:** 需要。识别质量与进度提示的清晰度需要人看。

## 接手时已知的运行时事实

- PaddleOCR 的 Python 与 PaddlePaddle 路径在桌面分发上是硬伤：依赖约 500MB，官方 pipeline 峰值内存 2.2GB、平均 CPU 占用约十核，8GB 目标机放不下。
- 可行路线是 RapidOCR 的 ONNX 模型经 ONNX Runtime 调用，代价是安装包每平台 +50–80MB、目标机 3–6 秒/页，另需一个图像预处理依赖——而后者与 ADR-0008 的原生依赖上限冲突，接手时须先处理这个冲突。
- Tesseract 许可证最干净、最好嵌入，但中文质量差一档，只在干净印刷体扫描上接近可用。

- [ ] 中文与英文的固定扫描页素材上产出可选中的识别文本
- [ ] OCR 进度可见，失败原因明确，用户可取消且取消后状态一致
- [ ] 由 OCR 文本形成的笔记出处含页坐标并可跳回
- [ ] 测试断言 OCR 过程无任何出站网络请求
- [ ] OCR 缓存产物不进入 Git 历史
