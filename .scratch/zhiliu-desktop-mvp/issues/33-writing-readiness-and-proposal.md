# 33: 写作就绪规则与提案审阅

**What to build:** 当某个主题积累到可能支撑一篇文章时，Agent 给出提案而不是直接动笔。提案是结构化的证据集合而非文稿：论点、支撑的思想笔记、来源证据、AI 推演，以及被识别出的缺口与薄弱推理，让用户在生成之前就能检查这套理由。用户确认或修改论点、逐条纳入或排除证据。写作就绪的条件是一个用户确认的论点加上至少三条思想笔记——这与主题成为思想线索的阈值是同一个条件，不是两个。

确认必须逐项进行，不存在一键批量确认：这依据 ADR-0003 的同一个理由，确认是论点成为用户自己的那一刻，批量化会把它变回一个标签。这一点不能靠断言「界面上不存在批量入口」来验证——实现之前界面根本不存在，那条断言天然通过，永远不会红。它的可断言形式是确认记录的数量必须等于用户实际的操作次数。

**Blocked by:** 24, 29

**Status:** done

**Starting failing test:** 用两条思想笔记构造主题，断言无法进入正式草稿；补到三条后断言可以；对该提案的 N 条证据逐条确认，断言产生 N 条独立的确认记录且确认记录数等于操作次数。

**Demo acceptance:** 需要。提案是否真的让人看清理由与缺口，只能人判断。

- [x] 提案展示论点、支撑思想笔记、来源证据、AI 推演与识别出的缺口
- [x] 提案是结构化证据集合，不是 Markdown 文稿
- [x] 提案被持久化并纳入自动 Git 追踪，作为「用户确认了什么」的记录（承接票 11 声明的追踪范围）
- [x] 用户可以确认或修改论点
- [x] 论点由 AI 起草时，用户直接确认即视为确认，但记录中保留该论点由 AI 起草的事实
- [x] 确认逐项进行：对 N 条证据逐条确认后产生 N 条独立的确认记录，且确认记录数等于用户实际操作次数（ADR-0003 的同一理由）
- [x] 用户可以逐条纳入或排除提案中的证据
- [x] 测试断言不满足「一个确认论点 + 至少三条思想笔记」时无法进入正式草稿
- [x] 缺乏个人思想支撑的主题保持为提案，不被表述为用户的声音
- [x] 缺失证据与薄弱推理在起草之前被明确指出
- [x] 「需要修复」状态的笔记不计入写作就绪，修复后重新计入（承接票 16）
