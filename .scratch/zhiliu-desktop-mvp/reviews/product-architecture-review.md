# 领域模型与 ADR 评审 (第 1 轮)
- 日期: 2026-08-30
- 评审方式: subagent
- 结论: 需修改

> 返工后票号已全量变更，本报告中的票号一律指旧号，换算见 `round-1-followup.md`。`CONTEXT.md` 的行号引用指返工前的版本。

## 发现项

- [严重] `CONTEXT.md` **Thought Signal**(第 63–65 行) 与 **Writing Readiness**(第 81–83 行): Thought Signal 自称阈值「the same threshold as Writing Readiness」，但两条定义写的条件不同——Thought Signal 只要求「至少三条思想笔记」，Writing Readiness 要求「一个已确认论点 + 至少三条思想笔记 + 至少两个不同来源文档」。这个「一致」的断言按文件自身的定义即为假。下游已经分叉：票 20 写「阈值为三条思想笔记，与写作就绪一致」，票 27 的起始失败测试却断言「三条同一本书的笔记不能进入正式草稿」。→ 二选一并写死：要么 Thought Signal 也带双来源约束（则两处条件文字必须逐字相同），要么删掉「the same threshold as」这句自洽性断言，改为显式列出两个独立门槛及其关系，并同步票 20 的措辞。
- [严重] `CONTEXT.md` **Writing Readiness**(第 82 行) 对 `spec.md` 的静默偏离: 「at least two different Source Documents」这一约束在 spec 中不存在——US 78(第 100 行) 与 Implementation Decisions(第 183 行) 都只写「one user-confirmed thesis and at least three supplied or explicitly accepted user thoughts」。术语表凭空收紧了准入条件，且已进入票 27 的验收清单与失败测试，成为可执行断言。协议要求与上游冲突必须明说而非静默覆盖，而术语表不是记录决策的地方，因此这条偏离目前没有任何理由留档。→ 若确实要加双来源约束，为它开一份 ADR（难以逆转、改动会失效已生成内容、明确声明与 spec 第 183 行冲突及为何 spec 的规则不足）；若不要，从 `CONTEXT.md` 与票 27 一并删除。
- [严重] `CONTEXT.md` **Topic Origin**(第 59–61 行) 与 **Library Discovery**(第 67–69 行) 对 ADR-0002 的分类不完备: ADR-0002 把 Origin 定义为二值推导——「computed from whether at least three Thought Notes support the Topic」；而 Library Discovery 被定义为「supported **only** by evidence drawn from Source Documents」。于是「有 1–2 条思想笔记 + 源证据」的主题两边都不属于：不满足三条门槛，也不是「只有源证据」。Topic Origin 是唯一守住核心信任承诺的闸门，未定义值的默认落法（落到 Library Discovery 还是待定）会直接决定它会不会被自动试写。→ 明确第三种状态或改写 Library Discovery 的定义使二值划分穷尽（例如「supported by fewer than three Thought Notes」），并在 ADR-0002 里写明未达标主题的归属。
- [严重] `CONTEXT.md` 各术语 `_Avoid_` 列表与本文件的规范名冲突: **Vault**(第 11 行) 让人避免 `library`，而 **Library**(第 17 行) 是规范名；**Provenance**(第 47 行) 让人避免 `origin`，而 **Topic Origin**(第 59 行) 是规范名；**Manuscript**(第 87 行) 让人避免 `draft` 与 `草稿`，而 Manuscript 自己的状态值就是 **Draft**(第 86 行)；**Atomic Note**(第 33 行) 让人避免 `note`，而 **Thought Note** 是规范名；**Source Position**(第 23 行) 让人避免 `citation`，而 **Source Document**(第 14 行) 和 Source Position 自己的定义句都在用 `citation`，spec 的导出脚注/来源清单(第 192 行) 同样以 citation 为规范概念；**Reading Status**(第 25–26 行) 让人避免 `progress`，定义句自己写 `progress through`；**Topic**(第 57 行) 让人避免 `group`，定义句自己写 `grouping`；**Generation Trace**(第 111–113 行) 让人避免 `record`，定义句自己写 `The local record of`；**Background Budget**(第 107–109 行) 让人避免 `limit/cap`，而 spec 第 177 行与票 19 通篇用 caps。术语表是 AI 实现者唯一的命名法，`_Avoid_` 与规范名互相拆台会直接产出错误的字段名与类型名。→ 逐条重扫 `_Avoid_`：只列真正禁止的同义词，凡是本仓库在别处规范使用的词（library、origin、citation、draft、note、cap）从禁用表移除，或改为限定式说明（如「不要用 library 指 Vault」）。
- [严重] `CONTEXT.md` 缺失 **Style Profile**(写作风格档案): spec 用 8 条 user story(US 99–106) 定义它，并把它列为「first-class, readable artifact with manual editing, reset, version history, and evidence-linked proposed updates」(第 194 行)，票 31、32 直接实现它，票 17 把它纳入自动 Git 追踪。它有版本、有证据、有确认流程，是本产品第二个「AI 不得静默改写用户」的载体，却在术语表和 10 份 ADR 里零出现，中文名也未锁定。→ 补入 Style Profile 术语（含中文对照与 `_Avoid_`），并为「风格档案更新必须带证据且经用户确认」这一难以逆转的规则判断是否需要 ADR。
- [严重] ADR-0004 与 `spec.md` US 70/73(第 92、95 行) 及 Implementation Decisions(第 187 行) 的未声明冲突: ADR-0004 断言全系统「one three-valued vocabulary — User, Source, AI — at every layer」，`CONTEXT.md` **Provenance**(第 46 行) 复述为「There is exactly one such vocabulary」。但 spec 要求知识库对话按段落标注「evidence-backed 还是 model supplementation」，这是一套二值词汇，票 24 已按此实现。两套标签如何映射（evidence-backed 对应 Source 还是 Source+User，model supplementation 是否等于 AI）无人规定，而 ADR-0004 的全部理由正是「不要映射层」。→ 在 ADR-0004 中显式处理对话标签：要么声明对话段落复用三值词汇并说明取值规则，要么声明这是有意的第二套词汇、给出映射并承认这与本 ADR 的「唯一词汇」表述冲突。
- [一般] ADR-0005 的安装包体量(第 13 行) 与 ADR-0007 的模型体量(第 3 行) 算术不相容: ADR-0005 称安装包 130–250 MB，ADR-0007 称模型 124 MiB(≈130 MB)，spec 第 170 行要求 Embedding 是 bundled。Electron 运行时本体加上 ONNX Runtime 各平台二进制已在百 MB 量级，再叠加 130 MB 模型，130 MB 的下界不可能成立。ADR-0005 恰恰是拿体量当作选型代价来权衡的，这个数字失真会误导后续所有「体量是否可接受」的判断。→ 要么修正 ADR-0005 的区间并注明是否含模型，要么在 ADR-0007 说明模型首次运行下载而非随包分发（并处理离线首次运行与 spec「bundled」的措辞冲突）。
- [一般] ADR-0006(第 8 行) 与 ADR-0008(第 7 行) 以互不相容的单位给同一语料定容量: ADR-0006 以「20 万 chunk × 384 维」推导出 77 MB 并据此认定暴力检索够用，ADR-0008 则以「ten thousand notes」论证 `LIKE` 回退扫描便宜。spec 的规模目标是「约 10,000 条原子笔记」(第 171 行)，但全文检索与语义检索都要覆盖书籍与网页(US 49、50)，而书籍语料的 chunk 数与笔记数不是一个量级。两份 ADR 都没写 200,000 这个数从哪来、书籍语料算不算在内。「Faiss、LanceDB、HNSW 解决的是我们没有的百万级问题」这个结论完全依赖这个未交代的前提。→ 在 ADR-0006 写出 chunk 预算的推导（笔记数 × 每笔记 chunk + 书籍数 × 每书 chunk），并在 ADR-0008 用同一单位重述 `LIKE` 回退的扫描成本；给出「超过多少 chunk 就重新评估暴力检索」的量化复核触发。
- [一般] ADR-0007 内部自相矛盾(第 3 行 对 第 7 行): 正文说选 bekko 的理由是它在跨语言与概念召回上「is strongest exactly there」，Considered Options 却说 granite「is the fallback if cross-language recall proves insufficient in practice」。若 bekko 在跨语言上最强，那么跨语言不足时换到一个（按本 ADR 自己的叙述）跨语言更弱的模型是无效退路。这条退路是 ADR 唯一的风险兜底，写错会让下游在真出问题时走向错误动作。→ 明确 granite 强在哪个维度（聚合检索分 60.3 对 56.2 是哪个基准、是否含跨语言子集），并把退路条件改写成可判定的形式（触发指标 + 换模型 + 全库重建索引的代价）。
- [一般] ADR-0009 第 5 行的冲突声明不完整: 它只声明与 spec 的 Implementation Decisions(第 161 行) 冲突，但 OCR 移出范围同时使 spec 另外两处失效——Testing Decisions 第 219 行仍要求「OCR acceptance tests 断言可选中的识别文本与页坐标链接」，Out of Scope 第 263 行仍写「Local Embeddings and OCR are supported」。在无人复核的实现路径上，一个照 Testing Decisions 建套件的实现者会为一个不存在的能力写验收测试。→ 在 ADR-0009 中逐条列出被它作废的 spec 位置（第 161、219、263 行），并说明 US 111 与第 198 行里的「OCR caches」在本版本内为空。
- [一般] ADR-0010 未声明与 `spec.md` 的偏离: spec Implementation Decisions 第 205 行写「Releases are unsigned Windows and macOS installation packages」，Out of Scope 第 268 行把「Signed binaries」明确排除，US 121 也以「unsigned releases」为用户契约；ADR-0010 决定 macOS 产物用稳定自签证书签名。这是对 spec 明确「no」的修改，却没有像 ADR-0009 那样声明冲突。ADR-0005 第 3 行还把「unsigned packaging on both platforms」当作选型约束之一，措辞上与 ADR-0010 直接打架。→ 在 ADR-0010 补一段冲突声明（区分「自签名」与「Developer ID 签名 + 公证」，说明 spec 的「unsigned」实际所指），并同步 ADR-0005 的约束表述。另外「证书成为长期项目机密」只写了后果，没有决定保管方式，与 spec 第 176 行「凭据只进系统凭据库」的原则没有接口——需要一条明确的托管决定或一张票。
- [一般] `CONTEXT.md` **Manuscript**(第 85–87 行) 的 kind × status 取值空间未定义: kind 是 Trial|Formal，status 是 Draft|Final，四个组合中「Trial + Final」在 ADR-0003 之下不存在含义，术语表却没有排除它。同时英文 **Formal**(kind) 与 **Final**(status) 词形相近、中文侧 **Formal Manuscript** 的 `_Avoid_` 又禁用「定稿」，而 status Final 的中文对照根本没给。→ 给 Draft/Final 补中文对照，写明合法组合（或改成单一状态机），并让 **Trial Manuscript** 与 **Formal Manuscript** 的定义显式说明各自可取哪些 status。
- [一般] `CONTEXT.md` 混入了属于 ADR 与 spec 的规则和理由: **Topic Origin**(第 60 行)「— which is what stops corpus opinions from being presented as the user's own」是 ADR-0002 的论证；**Thought Signal**(第 64 行)「so that qualifying as the user's own idea and qualifying to be written are one condition rather than two」同上；**Provenance**(第 46 行)「retrieval ranks User ahead of Source ahead of AI」是 spec 第 186 行的排序决策；**Reading Status**(第 26 行)「Reading follows from real local progress… No analysis or summary moves it」是 spec 第 165 行的行为规则；**Trial Manuscript**(第 90 行)「It can never become Formal in place; at most it pre-fills a Proposal」是 ADR-0003 的整条决定；**Suggestion Inbox**(第 72 行)「Deliberately not a system notification」是产品决策；**Generation Trace**(第 112 行) 直接列出七个字段，属于特性级字段细节。格式规范要求术语表只定义「是什么」，一到两句；现在同一条规则同时存在于术语表、ADR 与 spec 三处，改一处就静默失同步。→ 把理由与规则移回对应 ADR/spec，术语表只留下辨识该概念所必需的定义句，需要时以「见 ADR-000N」引用而不复述。
- [一般] `CONTEXT.md` **Library Discovery**(第 67–69 行) 与 **Proposal**(第 77–79 行)、**Writing Readiness**(第 81–83 行) 构成死路: Library Discovery 按定义「only」由源证据支撑，因此永远不含思想笔记，也就永远无法满足 Writing Readiness；它「Receives Proposals」，但这些 Proposal 结构上不可能通往 Formal Manuscript。spec US 82 只说库发现给提案，同样没写用户怎么把它变成自己的东西。→ 在术语表或 ADR 中写明库发现型 Proposal 的出路（例如用户在其上补写思想笔记后主题的 Origin 随证据翻转为 Thought Signal），否则下游会实现一个用户点不动的界面。
- [一般] `CONTEXT.md` 缺失若干 spec 反复使用、下游必须命名的概念: **Thesis**(论点)——Writing Readiness 与 Proposal 的定义都以它为轴，票 27 还给它加了「由 AI 起草但被用户确认」的状态，却没有术语；**Conflict Copy / 合并决策**(US 41–42、spec 第 169 行、票 15)——它与 **Parallel Revision** 都是「同一段文字并存两版」，不命名必然被实现者混为一谈；**Prompt Override**(US 107–108、spec 第 196 行、票 33)——是 Git 追踪对象却无术语；**索引状态 / 部分索引**(US 16、spec 第 172 行)——检索与 Agent 都要对外暴露它。→ 补入这四个术语，其中 Conflict Copy 必须在定义里写明与 Parallel Revision 的区别（外部编辑冲突 vs AI 改写）。
- [建议] ADR-0003 基本是 `spec.md` 第 185 行的复述: spec 已经写明「Automatic trial drafts… remain separate from formal articles until the user confirms the thesis and material」，ADR-0003 增量只有「Trial 保留为历史」与「确认提案产生一份新的 Formal Manuscript」，且没有记录任何被否决的替代方案。它满足「无上下文会显得奇怪」，但「真实权衡」一节缺失。→ 补一句被拒绝的方案与拒绝理由（例如「加一个转正按钮并记录来源」为何不够），否则它只是 spec 的第二份副本。
- [建议] ADR-0005 第 15 行「Minimum supported OS becomes macOS 13」缺少因果: 前后文没有任何一句解释这个下界从何而来（Electron 版本？WKWebView？签名机制？），而它是对用户可见的硬约束。→ 补一句来源。
- [建议] ADR-0007 第 3、7 行单位与基准不一致: 主选模型写 124 MiB，替代方案写 98 MB，MiB 与 MB 混用使「smaller」的比较尺度不统一（124 MiB ≈ 130 MB）；「aggregate retrieval 60.3 against 56.2」未说明是哪个基准的哪个子集，而 Qwen3 的 66.33 明确是 C-MTEB，三个数字并列易被读成同一标尺。→ 统一为 MB 或 MiB，并给每个分数标注基准名。
- [建议] ADR-0006 第 8 行「perfect recall at 20」用作论据是同义反复: 暴力检索本身就是精确检索，recall@20 = 1 是它的定义而非某个基准的测量结果，把它列为「published benchmarks」的结论会让读者误以为量化后仍需验证召回。同一句里「under 75 ms from disk」与「under 4 ms quantized in memory」两个数的适用条件也未区分（是否同一硬件、是否含解量化）。→ 改写为「量化后的暴力检索仍是精确检索，因此只需验证延迟」，并标注两个延迟数各自的条件。
- [建议] ADR-0006 标题与正文范围不一致: 标题写「vectors only for cross-language recall」，正文与 Consequences 写「cross-language **and conceptual** recall」，票 09 采用后者。标题是最常被单独引用的一行。→ 标题补上 conceptual。

## 核实与清单适用性

已核实为准确、不作为发现项的三处:

- ADR-0009 「Three of the spec's user stories move out of scope」数字正确: spec 中直接依赖 OCR 的 user story 恰为 US 13、14、27 三条；US 111 只在忽略清单里提及 OCR 缓存，不构成第四条。
- ADR-0006 的 77 MB 算术正确: 200,000 × 384 × 1 byte = 76.8 MB。
- spec 第 283 行要求的六份 ADR 无遗漏: 桌面框架 → ADR-0005；本地检索/Embedding 运行时 → ADR-0006/0007/0008；OCR 运行时 → ADR-0009；知识库结构与稳定标识 → 票 02 待产出；Agent 执行模型 → 票 18 待产出；Git 集成 → 票 17 待产出。

`references/product-architecture-checklist.md` 的下列条目本轮**不适用**，原因是本仓库没有 `product/architecture.md`，其角色由 `CONTEXT.md`（术语）与 `docs/adr/`（决策）承担，二者都不是系统地图，不承载模块划分与开发视图:

- 架构特征 3~5 个及质量属性场景、原则与风格 — 不适用。ADR 只记录单点决策，没有也不应有特征清单。
- 依赖方向、模块/上下文 3–7 个、开发视图「新代码放哪/测试放哪」、关键场景作垂直切片判据 — 不适用。垂直切片判据由 `.scratch/zhiliu-desktop-mvp/issues/` 的 38 张票承担，测试缝由票 01 确立。
- 演进节的演进路径与适应度函数 — 不适用于 ADR 集合；但 ADR-0006 的「谁想把向量提为主力必须先重测中文检索」与 ADR-0008 的「加第二个原生依赖必须先论证」已是等价的复核触发，只缺量化阈值（见 ADR-0006 相关发现项）。
- 「多上下文时有 CONTEXT-MAP.md」 — 不适用。本仓库为单上下文，根目录单 `CONTEXT.md` 符合 `docs/agents/domain.md` 的约定。
- 「未把特性级接口/字段细节塞进产品架构」 — 适用且已按此判定，见 **Generation Trace** 字段列表一项。
- 「难逆转点进 ADR 而非堆在正文」 — 适用且已按此判定，见「术语表混入 ADR 与 spec 规则」一项。
- 「正文 ≤120 行量级」 — 适用且通过: `CONTEXT.md` 113 行，10 份 ADR 共 93 行。
