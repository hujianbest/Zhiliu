# macOS builds are signed with a stable self-signed certificate

The first release is neither signed with a paid Developer ID nor notarised, but both naive alternatives fail badly. Shipping entirely unsigned produces "app is damaged and should be moved to the Trash", which has no path around it in the interface at all. Pure ad-hoc signing fixes that, but it pins the signature's designated requirement to the binary's content hash, and macOS ties folder-access permissions to code signature identity — so every release would silently revoke the user's permission to read their own Vault while System Settings continued to display that permission as granted, which is close to the most confusing failure mode available. A stable self-signed certificate keeps the identity constant across releases and degrades the first-launch failure to the "unidentified developer" dialog, which a user can get past.

This contradicts the spec, which says releases are unsigned Windows and macOS packages (line 205), lists signed binaries under Out of Scope (line 268), and makes "unsigned releases" a user-facing contract in US 121. What the spec is excluding is a paid Developer ID identity and Apple notarisation, both of which remain out of scope here. A self-signed certificate costs nothing, involves no Apple account, and is invisible to the user except that the first-launch dialog is the passable one rather than the impassable one. We read the spec's "unsigned" as "unnotarised and without a paid identity" and satisfy it in that sense; ADR-0005's constraint list is worded the same way.

## Consequences

- The certificate and its private key become a long-lived project secret, and the one secret that cannot live where every other credential lives: the OS credential store of a user's machine is the wrong place for a build-time key. It is held in the build machine's login keychain with an offline encrypted backup kept outside the repository, and ticket 06 records both the export procedure and the recovery path. Losing it forces every existing user to re-grant folder access.
- Windows still shows a SmartScreen warning on every release, and unsigned files rebuild reputation from zero each time; Smart App Control on Windows 11 may block execution outright. This is documented for users rather than solved.
